# IVXV PoC
## Structure
- `env.sh`: environment path variables
- `setup-cs.sh`: prepares the local ivxv collector/core Go code for the CS PoCs by rebuilding the generator and regenerating the required gen_types.go
- `iv/uv-*`: subfolder for the corresponding vulnerability, containing data used by test cases in the private mirror of ivxv and ivotingverification repos.

## Setup
Start in the PoC root:
```sh
source ./env.sh
```

Clone private mirror repos under `repos/`:
```sh
mkdir repos
cd repos
git clone git@github.com:pogen300/ivxv.git
git clone git@github.com:pogen300/ivotingverification.git
```

Keep using the same shell for all CLI PoC tests

### CS setup
Set up CS-side Go workspace for CS PoCs
```sh
./setup-cs.sh
```

### Intellij projects setup
- Add `IVXV_POCROOT=/Users/www-data/Desktop/ivxv-project/ivxv-poc` to the run config of any test file

#### PA setup
Open `ivxv/processor` in Intellij

#### VVD setup
Open `ivotingverification` in Intellij

#### Audit setup
Open `ivxv/auditor` in Intellij


## IV-V2

Run in IDE:
- VVD: `repos/ivotingverification/app/src/test/java/ee/vvk/ivotingverification/util/IVV2VVDTspDigestMismatchTest.java`
- PA: `repos/ivxv/common/java/src/test/java/ee/ivxv/common/service/bbox/impl/IVV2PATspDigestMismatchTest.java`

Expected result:
- VVD accepts the same forged response
- PA rejects the forged response with `REG_NONCE_ALG_MISMATCH`

### PoC Implementation
#### Data
- `iv-v2/collector-public.pem`: a demo TSP client key
- `iv-v2/request.tspreq`: TSP request
- `iv-v2/response.tspreg`: TSP response generated by BouncyCastle as a valid RFC3161 response over the forged request using the TSA's key
- `iv-v2/signature-value-canon.bin`: signature used for creating the TSP request
- `iv-v2/tsa-cert.pem`: a self-signed TSA certificate with critical timeStamping EKU

`iv-v2/request.tspreq` contains mismatching digest algorithms used for `m` and `n`. Running the following commands and observe that `m` uses SHA512 and `n` uses SHA256:
```sh
openssl ts -query -in iv-v2/request.tspreq -text
openssl asn1parse -inform DER -in iv-v2/request.tspreq
openssl asn1parse -inform DER -in iv-v2/request.tspreq -strparse 92
```
#### Scripts
- `IVV2VVDTspDigestMismatchTest` uses the real VVD-side `Pkix.java` parser.
- `IVV2PATspDigestMismatchTest` uses the real PA-side TSP verifier and checks that it throws `REG_NONCE_ALG_MISMATCH`.


## IV-V5
Run CS test:
```sh
cd "$IVXV/common/collector"
go test ./crypto/elgamal -run TestIVV5CSAcceptsNegativeASN1Ciphertext -count=1
```

Run in IDE:
- VVD `repos/ivotingverification/app/src/test/java/ee/vvk/ivotingverification/common/crypto/elgamal/IVV5VVDNegativeCiphertextTest.java`
- PA `repos/ivxv/common/java/src/test/java/ee/ivxv/common/crypto/IVV5PANegativeCiphertextTest.java`


Expected result:
- CS accepts the malformed ciphertext
- VVD accepts the malformed ciphertext
- PA reports `INVALID_RANGE`

### PoC Implementation
`iv-v5/negative_modp3072_ciphertext.b64` contains a strategically created vote ciphertext `(A,B)` with:
- `A`: a negative ASN.1 `INTEGER`
- `B`: ASN.1 `INTEGER` value `1`

`B = 1` was chosen as a trivially valid quadratic residue for all three actors. `A` was chosen to satisfy three conditions:
- CS accepts it after parsing the ASN.1 integer as signed and then reducing it modulo `p`
- VVD accepts it because `getPositiveValue()` interprets the same DER bytes as an unsigned positive integer that still passes the ciphertext validations
- PA rejects it because its ASN.1 interpretation preserves the negative sign and `ModPGroup.isGroupElement()` returns `INVALID_RANGE` for values `<= 0`

## P-V1
Run CS test:
```sh
cd "$IVXV/common/collector"
go test ./crypto/elgamal -run TestPV1CS -count=1
```

Run in IDE:
- VVD `repos/ivotingverification/app/src/test/java/ee/vvk/ivotingverification/common/crypto/elgamal/PV1VVDWeakGeneratorTest.java`
- PA `repos/ivxv/common/java/src/test/java/ee/ivxv/common/crypto/PV1PAWeakGeneratorTest.java`

Expected result:
- CS accepts malformed serialized generators and accepts the `g=1,y=1` ciphertext
- PA accepts id and non-QR generator
- VVD accepts id and non-QR generator

### PoC Implementation
#### Data
- `p-v1/weak-g1-y1-public.pem`: ModP public key with the original safe-prime modulus but weak parameters `g=1,y=1`
- `p-v1/weak-nonqr-y1-public.pem`: ModP public key with the same modulus but a non-QR generator `g=p-1`
- `p-v1/weak-g1-y1-ciphertext.b64`: ciphertext with `A=1` and `B` equal to a valid encoded plaintext element
- `p-v1/weak-g1-y1-randomness.b64`: matching randomness for VVD decryption
- `p-v1/weak-g1-y1-plaintext.txt`: matching plaintext for VVD decryption

#### Tests
- `TestPV1CSAcceptsWeakGeneratorParameters`, `TestPV1CSAcceptsWeakGeneratorCiphertext`: use the real CS's X.509 unmarshaller and ciphertext validator
- `PV1PAWeakGeneratorTest`: uses the real PA ElGamal pk parser and `CorrectnessUtil.isValidCiphertext()`
- `PV1VVDWeakGeneratorTest`: uses the real VVD's `parseX509PEMPublicKey()` and `decryptWithRandomness()`
